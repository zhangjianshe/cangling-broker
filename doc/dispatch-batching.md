# 批量领取与消息分发优化（2026-10-30）

本次修改基于 `fb010e0`（0.1.70），用于进一步优化已采用 pending 覆盖索引的消息分发。
本文记录实现与本地隔离测试；生产部署结果以对应版本的发布记录为准。

## 实现

- `CL_BROKER_CLAIM_BATCH_SIZE` 默认 16，可设 1–128，实际批次不超过订阅当前剩余的
  `CL_BROKER_CONSUMER_PREFETCH` 配额。设为 1 可在同一程序中对比逐条领取。
- 一次原子 `UPDATE ... WHERE id IN (SELECT ... LIMIT ?) RETURNING ...` 领取一批，沿用
  pending 覆盖索引。保留 topic 隔离、到期时间过滤、attempts 和 lease 条件。
  SQLite 不保证 RETURNING 顺序，因此在内存中按创建时间排列这一小批消息。
  同创建时间的消息不承诺全局顺序，多个消费者也不保证处理完成顺序。
- 先预留 prefetch 配额再领取。未发送消息等待超过半个可见性超时后归还队列；断连或停机时
  也归还本地缓冲的未发送消息。归还同时重置可领取时间并通知订阅者。ACK 截止时间沿用
  本批领取时的租约截止时间，避免每条消息重新获得完整 ACK 等待窗口。
- 通配订阅按各分片中的就绪主题匹配，并轮换起始分片/主题；不再只检查最早的 64 条消息。
  MQTT 的 `+`、`#` 和 `$SYS` 排除规则仍由统一匹配函数处理。
- 移除增减式队列深度缓存。状态接口从各分片中的 pending/processing 行统计实际深度，
  新增部分覆盖索引 `idx_messages_active_depth(topic, status)`，避免扫描保留的已投递 payload。
  各分片读取时点可以略有差异；静止后计数与数据库一致，不会残留缓存漂移。
- 保留已有 ACK 批量写入机制。

## 性能指标

`/status` 和受保护的 `/status/details` 增加 `performance` 对象。每项包含：

- `count`、`total_us`、`max_us`；
- `bucket_upper_us` 和 `buckets`：非累计直方图，最后一个桶为超过最大边界的样本。

所有时长均为微秒；计数从进程启动累计，重启清零。原子计数的并发快照是近似值。

| 字段 | 样本单位与含义 |
| --- | --- |
| `admission` | 每次非重复入队请求的处理及有界通道背压等待 |
| `write_queue` | 每条消息从尝试入队至开始准备数据库写入，包含通道背压及收集批次等待 |
| `persist_batch` | 每个写入批次的数据库处理耗时，包含失败后的重试等待 |
| `claim_batch` | 每次精确主题批量领取 SQL 的耗时，包含数据库连接等待；不含通配主题发现 |
| `queue_wait` | 持久化消息创建至开始分发的耗时，包含排队、领取和本地缓冲等待 |
| `send` | 每条消息构建并写入订阅输出通道的耗时；不是客户端实际接收时间 |
| `ack_wait` | 每条持久化消息发送后等待 ACK 的耗时；超时也计入，不含完成写库 |
| `ack_commit_batch` | 每个 ACK 完成批次写库的耗时 |

通配主题发现耗时目前未单独计量；如生产环境通配吞吐仍不足，应继续检查这一阶段。
可临时启用 debug 日志查看领取批次大小和逐消息分发耗时；不建议长期逐条记录高流量日志。

## 验证方式

```bash
cargo test --locked -- --test-threads=4
cargo test --release --locked grpc_claim_batch_benchmark -- --ignored --nocapture
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings -A clippy::result_large_err -A clippy::derivable_impls
```

本机 Rust 1.99.1 的严格 Clippy 会对现有 tonic 生成代码和原有 model 的 Default 实现报错；
上述命令只排除这两项既有 lint，其余警告仍作为错误。

新增验证覆盖：并发批量领取不重复、批次上限、错误/旧 lease 拒绝、延迟重试排除、
归还后立即重新可投递、4096 条未来重试消息前置时的就绪消息领取、通配消息被 128 条同分片
无关消息遮挡、16 个忙碌分片中每片多个主题的轮换公平性、legacy 深度计数错误、
断连归还未发送缓冲，以及真实本地 gRPC 收发与批量 ACK。

基准为临时数据库、本地 TCP gRPC、256 字节 payload、4000 条固定积压、prefetch 32、
写入批次 128/等待 2ms、客户端每 32 条批量 ACK。比较 1、8、16、32 四种领取批次，
覆盖单主题、4 主题分别订阅及 4 主题通配订阅。每轮核对发布/接收 ID 集合、payload、
重复投递和最终 delivered/pending/processing。计时为订阅开始至全部完成写库的积压清空吞吐；
P50/P95 从数据库创建时间算至客户端接收，包含预先构建积压的时间。

这是本机隔离结果，不代表生产服务器容量。基准中的批次 1 也是本次修改后的实现，
用于控制变量比较，不等于完整的旧版本性能。大量未来重试仍需按创建时间跳过，未来可基于
指标决定是否拆分延迟调度队列；本次未改变重试调度架构。


## 验证结果

- 完整回归：90 passed，0 failed；1 个性能基准默认忽略，另行显式运行。
- rustfmt、diff 空白检查通过。
- Clippy 在排除上述两项既有 lint 后通过，其余警告均视为错误。
- 日志归档：`target/verification/dispatch-batching/`（本地构建目录，不进入 Git）。
